# Agent 约束规则：宠物洗护 B 端（店长·前台·服务·客服）（GoLand AI Assistant）

## 项目背景
单门店（shop_001）宠物洗护预约 O2O。C 端宠物主人预约支付，B 端四角色在同一份业务记录上协作：
- 店长：发布时段、日清核查、标记未到店、支付异常单登记
- 前台：到店核销
- 服务人员：登记服务开始/完成
- 客服：取消审批、退款失败跟进、支付异常退款

技术栈：Go / GoFrame / MySQL / Redis。
> 生成代码、接口、SQL、后台页面时必须遵守下列全部约束。状态、名额、金额口径与 C 端完全一致，禁止另立一套。

## 1. 状态枚举（唯一口径，与 C 端共用）
```
1 待支付  2 已确认  3 待客服审核取消  4 取消成功
5 已核销  6 服务中  7 服务完成        8 未到店
9 待支付超时关闭（系统写入，B 端只读）
```
允许的流转：
```
1 --支付--> 2 --核销(前台)--> 5 --开始(服务)--> 6 --完成(服务)--> 7
2 --≥2h取消--> 4（释放名额+退款）
2 --<2h取消--> 3 --同意--> 4 ;  3 --驳回--> 2
2 --时段结束未核销--> 8（店长标记，不退款）
```
❌ 禁止跳级、禁止直接 UPDATE status、禁止 B 端自定义状态值。

## 2. 角色与数据隔离
1. `shop_staff` 表：`staff_id / shop_id / role(1店长 2前台 3服务 4客服) / status`。
2. 所有 B 端接口先解析员工身份，再以 `staff.shop_id` 过滤数据，控制器不得直接拼 SQL。
3. 店长、前台、服务人员仅本店；客服为平台角色，按授权店铺访问（本题仅 shop_001）。
4. 禁止能力：代客下单、代客支付、改状态字段、删订单、改容量上限、改金额、干预 ≥2h 自动取消。

### 2.1 角色级禁止动作（越权即视为缺陷）
| 角色 | 不得执行 | 原因 |
|---|---|---|
| 店长 | 核销、发起或重试退款（兼岗须留痕） | 现场与资金动作应由专岗执行 |
| 前台 | 改时段、标记未到店、审批取消、退款 | 准入岗只判断是否到店 |
| 服务人员 | 核销、标记未到店、审批、任何资金动作 | 履约岗只登记过程 |
| 客服 | 核销、标记未到店、编辑时段、改金额 | 争议岗只处理取消与资金 |

> 实现要求：权限矩阵写在 `shop_staff.role` 判定中，禁止“店长账号万能”的写法。

## 3. 时段管理（店长）
1. 创建校验：结束晚于开始、开始晚于服务端当前时间、同门店不重叠；容量固定 3，忽略前端传值。
2. 时段状态：待生效（C 端可见）、暂停（C 端隐藏、后台保留）、进行中、已结束。
3. 存在状态 1/2/3 的预约时，禁止改时间、暂停、删除，返回 50002。
4. 暂停仅允许在无有效预约时执行，可随时恢复；暂停/恢复须写操作日志。
5. 时段列表容量只读。

## 4. 预约查询（全角色）
1. 支持日期→状态→手机号/宠物名/订单号模糊检索。
2. 字段：app_id、用户手机号、宠物名、时段、price、status、created_at。
3. 区分两类备注：`user_remark`（C 端填写，双向可见）、`shop_remark`（门店内部，C 端接口不返回）。
4. 列表页只允许查看与进入动作，禁止直接改状态。
5. **强制数据库层分页**，默认 20 条：预约列表（创建时间倒序）、审批列表（申请时间正序）、退款记录、异常单、操作日志。禁止全量查询后内存切片。
6. 点击宠物名可查该宠物在本店的历史预约（只读），不参与状态变更。

## 5. 核销（前台 / 店长）
1. 三重校验：本店员工（staff.shop_id 一致且角色为前台或店长）、`status=2`、不存在 `status=3`。
2. 状态 3 一律拒绝，返回 50004，禁止先核销后补审。
3. 核销成功 → 5，名额永久占用，永久退出取消退款流程。
4. 重复核销：`UPDATE ... WHERE status=2` 条件更新，影响行数为 0 即拒绝，收入不重复。
5. 核销与取消并发：仅先落库者成功，另一请求按最新状态失败。

## 6. 服务进度（服务人员 / 店长）
1. 只能 5→6（写 `service_start_at`）、6→7（写 `service_finish_at`），禁止跳级，返回 50009。
2. 未经核销的订单不得登记开始。
3. 重复点击完成返回“已完成登记”，收入只计一次。
4. 仅状态 7 计入已完成服务收入；5、6 占名额但不计收入。
5. 已核销及之后状态不提供取消入口，也不进入审批列表。

## 7. 未到店标记（店长）
1. 前置：`status=2` + 服务端时间晚于 `slot.end_time` + 未核销 + 无 `status=3`。
2. 时段未结束按钮置灰且接口拒绝，返回 50005。
3. `noshow_reason` 必填，前端与数据库双重非空，禁止默认值。
4. 标记后 → 8 终态：名额不释放、不自动退款、不可重复标记、不可提交取消。
5. 资金口径：计入已收款，不计入已完成服务收入。
6. 不实现争议退款裁决：不提供申诉、仲裁、判责退款入口，线下协商。

## 8. 取消审批（客服 / 店长兼管）
1. 审批列表仅 `status=3`；≥2 小时自动取消（已为 4）不进入列表，不可干预。
2. 同意：3→4，释放名额，生成 9900 分全额退款单（`refund_type=1`）。
3. 驳回：3→2，名额继续占用，恢复可核销，可填驳回原因并通知 C 端。
4. 一条申请只处理一次，处理后移出列表，不可撤回、不可改判，重复处理返回 50007。
5. 状态 3 期间：禁止核销、禁止标记未到店、禁止服务登记、禁止用户重复提交、名额冻结不释放。

## 9. 退款（客服）
1. 退款状态独立：1 待退款 / 2 成功 / 3 失败，与预约状态不联动。
2. `refund_type`：1 取消退款、2 重复支付退款；重复支付退款不得释放名额、不得改预约状态。
3. 重试只操作退款单，不改预约状态、不动名额、不恢复可服务。
4. 重试需记录次数、失败原因（渠道返回原文）、成功时间。
5. 取消成功即取消成功，退款失败也不得让预约重新可用。
6. 店长只读退款记录，返回 50008 拒绝任何退款写操作。

## 10. 支付异常单（店长 / 客服）
1. 产生条件：订单已关闭（status 9 或 4）后又收到支付成功，且交易号非重复推送。
2. 判定：同一 `transaction_id` 已存在 → 幂等返回不退款；不同交易号 → 登记异常 + 原路退款。
3. 处置三步：登记 `pay_exception` → 发起全额退款 → 保持预约关闭、名额不恢复。
4. 全程不触碰 `appointment.status`。
5. 异常单进入待处理清单，日清统计待处理数量；已处理不可重复登记，返回 50010。

## 11. 名额释放规则（全系统唯一入口）
名额只允许在以下四个场景释放，且只释放一次：

| 场景 | 触发方 | 释放时机 |
|---|---|---|
| 待支付超时关闭 | 定时任务 | 1 → 9 条件更新成功后 |
| 待支付主动取消 | C 端用户 | 1 → 关闭成功后 |
| ≥2 小时取消 | 系统 | 2 → 4 并生成退款单后 |
| 客服审批同意 | 客服 | 3 → 4 并生成退款单后 |

❌ 不可释放：已核销、服务中、服务完成、未到店（永久占用）；状态 3（冻结）；重复支付退款；核销先成功的并发。
释放必须集中在一个方法内：先 `SISMEMBER` 判断集合成员，`DECR` 后计数不得为负，为负即告警。其他任何地方禁止直接操作 `slot:{slotId}:quota`。

## 12. 当日台账与金额口径（店长，重点）
1. 按日期查询，按 `slot_id` 分组，数字支持下钻明细。
2. 五类计数：有效预约（2、3）、已完成（7）、取消（4）、未到店（8）、退款待处理（3 待审 + 退款中/失败）。
3. 四项金额独立：已收款（支付成功，按预约维度只计一笔）、已完成服务收入（仅 7）、已退款（退款成功含两类）、未退款（退款中+失败）。
4. ❌ 严禁把所有已付款计作已完成服务收入。
5. 聚合收敛到一个方法，前端不自行拼算；汇总与下钻必须一致。
6. 重复支付多收款项只出现在已退款/未退款，不冲减服务收入。

### 12.1 导出
1. 支持导出：预约台账、退款流水、未到店清单、支付异常单、日清汇总。
2. 必须为结构化明细（每行带 `app_id`），汇总行置顶且与页面数字完全一致。
3. 仅导出本店数据（客服按授权店铺），导出动作写 `oper_log`：操作人、时间范围、导出对象。
4. 禁止在导出中做口径改写或手工调整汇总。

## 13. 并发与幂等
1. 所有状态变更使用 `UPDATE ... WHERE status = ?` 条件更新，按影响行数判定成败。
2. 失败直接返回明确错误码，不重试、不补偿性二次执行。
3. 台账与明细不一致时以明细为准修聚合逻辑，禁止手工改汇总值。
4. 只读操作不得产生状态变更。

| 动作 | 角色 | 重复请求结果 | 拦截方式 |
|---|---|---|---|
| 核销 | 前台 | 提示已核销，收入不重复 | 状态 2 条件更新 + 核销判重 |
| 登记开始 | 服务 | 提示已登记开始 | 状态 5 条件更新 |
| 登记完成 | 服务 | 提示已完成登记 | 状态 6 条件更新 |
| 标记未到店 | 店长 | 提示已标记 | 状态 2 条件更新 + `noshow_at` 判重 |
| 审批取消 | 客服 | 50007 已处理 | 状态 3 条件更新 + `audit_result` 判重 |
| 退款重试 | 客服 | 提示处理中 | 退款单状态 + Redis SETNX 60s |
| 支付回调 | 渠道 | 幂等返回不退款 | `payment_log` 交易号唯一键 |

> 前端置灰只是体验层，服务端幂等是唯一有效拦截。

## 14. 时间口径
1. 所有业务时间判断取服务端时间，前端时间只做展示。
2. 取消窗口用秒级比较 `slot.start_time - now`，恰好 2 小时按 ≥2 小时处理。
3. 时段是否结束、未到店可否标记，均以 `slot.end_time` 与服务端时间比较。
4. 支付锁定时长由服务端写入 `lock_expire_at = now + 5min`，禁止前端倒计时决定关闭。
5. 禁止接收前端传入的时间参数参与业务判断。

## 15. 错误码
| 码 | 含义 |
|---|---|
| 50001 | 无权操作其他门店数据 |
| 50002 | 时段存在有效预约，不可修改/暂停/删除 |
| 50003 | 当前状态不可执行该动作 |
| 50004 | 存在待处理取消申请，暂不可核销 |
| 50005 | 时段未结束，不可标记未到店 |
| 50006 | 未到店原因必填 |
| 50007 | 取消申请已处理，不可重复审批 |
| 50008 | 无退款操作权限 |
| 50009 | 服务进度不可跳级，请先登记开始 |
| 50010 | 支付异常单已处理，不可重复登记 |

## 16. Go 实现规范
1. 分层 controller / service / repo；状态用常量 `StatusConfirmed = 2` 等，禁止魔数。
2. 状态变更统一走 `repo.CASUpdateStatus(ctx, appId, from, to, extra)`，影响行数 0 → 返回对应错误码。
3. 查询统一注入 `shop_id`；客服按授权店铺列表校验。
4. 操作日志 VERIFY / START / FINISH / NOSHOW / AUDIT / RETRY / EXPORT 必须写 `oper_log`。
5. 台账聚合单独封装，入参 `shop_id + date`，返回结构固定。
6. 列表查询必须带 `LIMIT/OFFSET`，禁止无分页全量查询。

## 17. 后台文案
- 核销成功：核销成功，该预约已进入服务流程
- 状态 3 拦截：该预约存在待处理取消申请，暂不可核销
- 未到店：已标记未到店，本次不自动退款
- 时段未结束：时段尚未结束，暂不可标记未到店
- 审批同意：已同意取消，退款已发起
- 审批驳回：已驳回，预约恢复有效，可正常到店
- 退款重试：已重新发起退款，请稍后查看结果
- 支付异常：该笔支付发生在订单关闭之后，已登记异常并发起退款
- 服务跳级：请先完成到店核销，再登记服务开始
- 台账提示：已收款与已完成服务收入分别核算，请勿混用

## 18. 红线禁止清单
❌ 跨门店查询或操作
❌ 直接 UPDATE appointment.status
❌ 删除用户预约订单
❌ 修改单场容量上限或订单金额
❌ 有有效预约仍改时段、暂停或删除
❌ 角色越权：店长退款 / 前台标记未到店 / 服务核销 / 客服改时段
❌ 状态 3 期间核销、标记未到店或登记服务
❌ 未核销直接登记服务开始，或跳级到完成
❌ 时段未结束标记未到店
❌ 未到店原因留空或写默认值
❌ 未到店自动退款或开放自助退款
❌ 店长发起或重试退款
❌ 退款重试时改动预约状态或名额
❌ 四个释放场景之外归还名额
❌ 把已收款当作已完成服务收入
❌ 手工修改台账汇总值或导出数字
❌ 拆掉 shop_id 隔离以便联调
❌ 用前端时间参与业务判断
