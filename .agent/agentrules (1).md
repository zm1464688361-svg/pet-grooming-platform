# Agent 约束规则：宠物洗护C端预约抢名额（GoLand AI Assistant）

## 项目背景

业务：宠物洗护预约系统，B端店长发布时段，C端宠物主人预约；单时段最大3只；使用 Go + GoFrame + MySQL + Redis Lua。

> 所有生成代码、接口、SQL、定时任务、结构体，必须严格遵守下面全部约束，禁止私自修改业务时序、状态流转、名额逻辑、支付幂等逻辑

## 1. 角色权限约束（强制）
1. 区分C端宠物主人 / B端（店长、前台、美容师、平台客服）
    - C端：只能操作自己user_id下的预约、自己宠物；**绝对不能实现：创建时段、核销、审核取消、标记未到店、退款重试**
    - 宠物是预置数据，C端仅查看，不做新增/编辑/删除宠物接口
2. 数据隔离：C端所有查询、更新SQL必须带上 `user_id = #{userId}`，禁止越权查询别人订单
3. 本规则只约束【C端预约链路】；B端能力不在本规则内实现
## 2. 时段准入约束（每次预约请求第一层Skill校验）
1. 只有店长发布、slot.status=1【可预约】、start_time > 当前时间 的时段，C端才可见、允许预约
2. slot.status=2（已开始）、slot.status=3（已结束），C端不展示、直接拦截预约
3. 单时段容量固定：maxCapacity = 3
4. 两条硬约束同时满足才允许创建预约订单：
    - 约束A：同一个 pet_id + slot_id，不存在有效预约（有效状态：1待支付、2已确认、3待审核取消）
    - 约束B：该时段当前有效预约总数 < 3
## 3. 名额扣减 & 释放时序（核心红线，严禁调换顺序）

✅ 固定时序：**DB事务提交成功、创建status=1待支付预约单之后，才调用Redis Lua占用名额**
❌ 禁止：先扣Redis名额再创建订单；禁止支付成功才扣名额

1. 名额占用：创建status=1订单成功 → Redis slot计数+1、petId加入slot pet_set集合
2. 锁定时长：5分钟，lock_expire_at = 创建时间 + 5min
3. 仅以下4种场景释放名额：
    - 场景1：用户主动取消 status=1 待支付订单
    - 场景2：定时任务扫描到 status=1 AND lock_expire_at < now，超时自动取消订单
    - 场景3：status=2 已确认，距离时段开始≥2h提交取消 → 自动审批到 status=4 取消成功
    - 场景4：status=3 待审核取消，客服审核同意 → status=4取消成功
4. 冻结规则：status=3【待客服审核取消】名额保持占用、**不释放、不可核销**
5. 永不释放名额场景：核销、服务中、服务完成、店长标记未到店，名额永久占用
6. Redis为缓存，MySQL appointment 表是真值源；Redis和DB不一致时只告警，不自动篡改业务数据
## 4. 订单状态枚举 & 流转（禁止新增状态、禁止私自跳转）

```
1: 待支付（生成订单，占用名额，5分钟倒计时）
2: 已确认（支付成功，名额继续占用，倒计时失效）
3: 待客服审核取消（名额冻结，门店不可核销）
4: 取消成功（名额释放，可关联退款单）
5: 已核销
6: 服务中
7: 服务完成
8: 门店标记未到店
9: 待支付超时关闭（终态）
```

流转规则：

1. 新建预约只能进入状态1
2. 仅状态1可以在5分钟内支付成功 → 流转为状态2
    - 边界：支付回调到达，订单已经超时关闭 → 禁止改成状态2，自动发起原路退款
3. 仅状态2允许提交取消申请：
    - 当前距离时段开始 ≥ 2h：自动审批，直接流转4，全额退款
    - 恰好剩余 2h：按 ≥2h 处理，走自动受理，边界不抖动
    - 当前距离时段开始 ＜ 2h：必须填写取消原因，未填拒绝提交；流转3，等待人工审核
    - 时间判据以服务端当前时间为准，与 start_time 秒级比较，禁止信任前端传参
4. 状态3分支：客服同意 → 4；客服驳回 → 2
    - 待审核期间：名额保持占用、不可核销、用户不可重复提交同一笔申请
5. 终态：4、5、6、7、8、9，不能回退到状态1，不参与抢名额
6. 状态1超时/主动取消，变为超时关闭终态，不再参与支付、名额逻辑
## 5. Redis Lua脚本约束
1. 两个Lua脚本：【占用名额】、【释放名额】分开写
2. 占用Lua：原子判断宠物是否已预约、名额容量；订单DB事务成功后调用
3. 释放Lua：仅命中上面4个释放场景才调用；必须先 SISMEMBER 判断是否占用，避免重复释放把计数减成负数
4. ❌ 禁止实现 先select判断count再update的并发写法，防止超卖
## 6. 定时任务约束（Go Cron）
1. 执行频率：每分钟执行一次
2. 扫描条件：`status = 1 AND lock_expire_at < NOW()`，只处理待支付
3. 处理顺序：条件更新订单为超时关闭（带 status=1 条件）→ 影响行数为1才调用Lua释放名额 → 记录日志
4. 定时任务**只处理status=1**，不处理其他状态；多实例部署下条件更新保证同一单只被处理一次
## 7. 支付回调接口约束
1. 根据订单号查询预约单
2. 前置校验：订单状态必须是 status=1
3. 校验签名、金额合法（金额必须等于 9900 分）
4. 通过：更新status=2，清空lock_expire_at
5. 非法回调（订单已超时、状态不是1）：拒绝确认支付，触发原路退款，返回渠道成功
## 8. 支付重复提交防护约束（新增，强制）

> 背景：用户连续点击支付按钮会并发发起两个支付请求，若都成功下单将产生两笔可支付凭证，极端情况重复扣款。

1. **前端交互层**：点击支付按钮后立即置灰并显示加载态，1.5秒内重复点击直接丢弃；收到“处理中”提示后不得立即恢复可点击状态
2. **服务端幂等锁**：生成支付参数前，必须以 `pay:lock:{appId}` 抢锁（SETNX + 30秒过期），抢锁失败直接返回 40008「支付请求处理中，请勿重复点击」，不调用渠道
3. **锁必须释放**：无论下单成功失败，处理结束 `defer Del` 释放锁，过期时间作为进程异常兜底
4. **状态前置校验**：只有 status=1 待支付可发起支付；其他状态返回 40009「当前状态不支持发起支付」
5. **渠道订单号幂等**：调用渠道统一下单时，`out_trade_no` 固定等于预约单号 appId，依赖渠道侧同号不重复下单
6. **回调幂等**：回调接口状态非待支付时直接返回成功，不做任何业务变更；重复通知不得重复确认、不得重复记账
7. **流水唯一键**：支付流水表 payment_log 以渠道交易号 `transaction_id` 建唯一索引，一笔真实资金只落一条记录
8. ❌ 禁止：只用前端防抖作为唯一防护；禁止用“先查锁再写锁”的普通缓存判断代替 SETNX
9. **两类通知必须分开判断**：
    - 同一 transaction_id 重复推送 → 幂等，只返回成功，**不退款、不改状态**
    - 两个不同 transaction_id → 判定重复扣款，**仅首笔确认预约，多余那笔单独退款**
    - 判定依据：同一 app_id 下是否已存在另一笔成功流水的不同交易号；先写入唯一流水者为首笔
10. **重复扣款处理**：首笔确认预约（状态置已确认、名额继续占用），多余款项生成独立退款单，原路退回；预约状态不再变更，收入只计一笔 9900 分
11. **退款来源区分**：refund 表增加 `refund_type`（1 取消退款 / 2 重复支付退款），重复支付退款**不得复用取消成功状态、不得释放名额**
12. **退款失败处理**：重复支付退款失败时预约仍保持已确认，用户正常到店服务；退款单转失败由客服重试，重试只动资金，不动预约与名额
13. **对账口径**：已收款按预约维度只计一笔；多付款项单列为待退款/已退款，不冲减服务收入，不得出现负实收
## 9. Go代码规范（GoFrame）
1. 使用 gf 框架，controller/service/repo分层
2. 数据库操作必须使用事务处理预约创建流程
3. 所有业务校验统一封装到 Skill 校验层，前端UI隐藏按钮只是辅助，后端必须二次校验
4. 结构体、注释清晰，状态写const常量（StatusPending / StatusConfirmed / ...），不要硬编码数字
5. SQL 禁止拼接，使用参数绑定
6. 增加日志：预约创建、Redis抢占、超时释放、支付回调、支付幂等拦截、取消申请
## 10. 返回提示文案固定（C端）

- 预约创建成功：预约成功，名额保留5分钟，请尽快完成支付
- 名额已满：该时段名额已抢光，请选择其他时段
- 宠物重复预约：该宠物已预约本时段，请勿重复预约
- 时段已开始：该时段已开始，无法预约
- 超时取消：预约超时未支付，订单已自动取消，名额已释放
- 支付处理中：支付请求处理中，请勿重复点击
- 支付成功：支付成功，预约已确认，请按时到店
- 提交取消（<2h）：已提交取消申请，等待客服审核，审核期间门店暂无法核销
- 退款失败：退款失败，请联系客服跟进，预约状态不受影响
- 未到店：门店已标记本次未到店，本次预约不自动退款

## 11. 错误码约定（C端）

| 错误码 | 含义 |
| --- | --- |
| 40001 | 宠物不属于当前用户 / 无权操作该预约 |
| 40002 | 时段不可预约或已开始 |
| 40003 | 名额已满 |
| 40004 | 同宠物在本时段已有有效预约 |
| 40005 | 订单已超时关闭 |
| 40006 | 当前状态不支持取消 |
| 40007 | 重复提交（幂等命中） |
| 40008 | 支付请求处理中，存在并发支付请求 |
| 40009 | 当前状态不支持发起支付 |

## 12. 红线禁止清单（绝对不能做）

❌ 调换时序：先扣Redis名额、再创建订单
❌ 支付成功才扣名额
❌ 私自状态跳转：待支付直接到取消成功、待审核直接核销
❌ status=3 提前释放名额
❌ 退款失败后恢复预约状态或重新占用名额
❌ C端开放任何B端能力（审核、核销、创建时段）
❌ 绕过pet_id+slot_id唯一约束，允许同宠物重复预约
❌ 时段已经开始仍然接收预约请求
❌ 定时任务处理非status=1订单超时逻辑
❌ 取消与核销并发时两方都执行成功
❌ 同一个 status=1 订单并发生成多笔支付单
❌ 不使用幂等键、不加锁直接调用渠道下单
❌ 把同一交易号的重复通知当成重复扣款去退款
❌ 两条不同交易号的通知都确认预约，导致重复记收入
❌ 重复支付退款复用取消成功状态或释放名额
❌ 重复支付退款失败后回滚预约状态
