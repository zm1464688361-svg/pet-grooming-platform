# Agent 约束规则：宠物洗护 C 端预约（GoLand AI Assistant）

## 项目背景
业务：宠物洗护预约系统。B 端店长发布时段，C 端宠物主人预约；单时段最多接待 3 只宠物，预约款固定 9900 分，未付款订单锁定名额 5 分钟。
技术栈：Go / GoFrame / MySQL / Redis Lua / 小程序。
> 生成代码、接口、SQL、定时任务、结构体时，必须遵守下列全部约束；禁止私自改动业务时序、状态流转、名额逻辑、取消政策与支付幂等逻辑。

## 1. 角色权限约束
1. C 端仅宠物主人，只能操作本人 user_id 下的宠物与预约；**不得实现创建时段、核销、审核取消、标记未到店、退款重试**。
2. 宠物为预置数据，C 端只读，不提供新增、编辑、删除接口。
3. C 端所有查询与更新强制带 `user_id` 条件，禁止越权访问他人订单。
4. 本规则集只覆盖 C 端预约链路，B 端能力不在范围内。

## 2. 时段准入约束（预约请求第一层校验）
1. 仅店长发布、`status=1` 可预约、`start_time > now` 的时段对 C 端可见、可约。
2. `status=2` 已开始、`status=3` 已结束的时段，C 端不展示且直接拦截。
3. 单时段容量固定 `maxCapacity = 3`。
4. 两条硬约束同时满足才允许建单：
   - 约束 A：`pet_id + slot_id` 不存在有效预约（有效状态 1、2、3）；
   - 约束 B：该时段有效预约数 < 3。

## 3. 名额扣减与释放时序（红线）
✅ 固定时序：DB 事务提交成功、生成 `status=1` 待支付订单之后，才调用 Redis Lua 占用名额。
❌ 禁止先扣 Redis 名额再建单；❌ 禁止支付成功后才扣名额。

1. 占用：建单成功 → Redis 计数 +1、petId 入集合。
2. 锁定：`lock_expire_at = now + 5min`。
3. 仅四种场景释放名额：待支付超时、待支付主动取消、已确认且 ≥2h 取消成功、待审核被客服同意。
4. `status=3` 待审核期间名额冻结：不释放、不可核销。
5. 核销、服务中、服务完成、未到店，名额永久占用不归还。
6. Redis 是缓存，MySQL 为真值源；不一致只告警，不自动改业务数据。

## 4. 状态枚举与流转
```
1 待支付  2 已确认  3 待客服审核取消  4 取消成功
5 已核销  6 服务中  7 服务完成        8 未到店   9 待支付超时关闭
```
1. 新建只能进入状态 1。
2. 仅状态 1 可支付成功 → 状态 2；回调晚于锁定到期时禁止确认，登记异常并退款。
3. 仅状态 2 可提交取消：
   - 剩余 ≥ 2h：自动受理 → 状态 4，全额退款；
   - 恰好剩余 2h：按 ≥2h 处理；
   - 剩余 < 2h：必须填原因，否则拒绝提交 → 状态 3；
   - 时间以服务端为准，与 `start_time` 秒级比较。
4. 状态 3：客服同意 → 4；驳回 → 2；期间名额占用、不可核销、不可重复提交。
5. 终态 4、5、6、7、8、9 不得回退到状态 1，不参与抢名额。

## 5. Redis Lua 约束
1. 占用与释放两个脚本分开编写。
2. 占用脚本原子判定宠物唯一与容量，事务提交成功后调用。
3. 释放脚本先 `SISMEMBER` 判断是否占用，避免重复释放把计数减成负数。
4. ❌ 禁止先查计数再更新的非原子写法。

## 6. 定时任务约束
1. 每分钟执行一次，扫描条件 `status=1 AND lock_expire_at < NOW()`。
2. 顺序：条件更新为超时关闭（带 `status=1` 条件）→ 影响行数为 1 才释放名额 → 记录日志。
3. 只处理状态 1；多实例下靠条件更新保证同一单只处理一次。

## 7. 支付回调约束
1. 依订单号定位预约，校验签名与金额（必须 9900 分）。
2. 状态为 1 才确认，更新为 2 并清空 `lock_expire_at`。
3. 状态非 1：登记异常、原路退款、返回渠道成功，不改预约状态。
4. 回调接口必须幂等，重复通知不得重复确认、不得重复记账。

## 8. 支付重复提交与重复扣款
1. 前端点击后置灰加加载态，1.5 秒内重复点击丢弃；收到“处理中”后不得立即恢复可点。
2. 生成支付参数前以 `pay:lock:{appId}` SETNX 加锁 30 秒，抢锁失败返回 40008，不调用渠道。
3. 处理结束 `defer Del` 释放锁，过期时间兜底。
4. 仅 `status=1` 可发起支付，其余状态返回 40009。
5. 渠道 `out_trade_no` 固定等于预约单号，依赖渠道侧同号幂等。
6. 两类通知分开判断：同一 `transaction_id` 重推 → 幂等不退款；不同 `transaction_id` → 重复扣款，仅首笔确认，多余一笔退款。
7. 支付流水表以 `transaction_id` 建唯一索引，先落库者为首笔。
8. 重复支付退款用 `refund_type=2` 独立记录，不释放名额、不改预约状态、不计收入。
9. 退款失败时预约仍为已确认，客服重试只动资金。

## 9. 时间口径与阈值
1. 5 分钟超时、时段是否开始、2 小时取消阈值，全部以服务端时间为准，禁止信任前端时间。
2. 与 `start_time` 做秒级比较，不做分钟取整，避免边界抖动。
3. 前端手机时间篡改不得影响任何业务判定。

## 10. 取消申请提交控制
1. 同一预约单同时只允许存在一条未结案取消申请。
2. `status=3` 时 C 端取消按钮置灰，禁止重复提交。
3. 客服驳回回到 `status=2` 后，才可再次发起。
4. 状态 5、6、7、8 不允许提交取消或退款申请。

## 11. 宠物与可选范围
1. 宠物下拉只展示当前用户绑定且状态启用的宠物，禁用宠物不可选。
2. 已核销、已完成的历史预约不限制该宠物预约新时段（不占用新旧名额）。
3. 同一宠物同一时段的有效预约校验仅针对状态 1、2、3。

## 12. 退款类型与展示
1. 两类退款：①预约取消退款 `refund_type=1` ②重复支付退款 `refund_type=2`，C 端需展示退款原因。
2. 当前业务只支持全额退款，不支持部分退款，退款金额恒等于原支付金额。
3. 退款失败时 C 端只展示失败原因与联系客服提示，不提供自助重试。
4. 退款是独立子流程，退款状态变化不回滚预约状态。

## 13. 通知与预约须知
1. 需推送：预约创建成功、支付成功、超时自动取消、取消审核同意/驳回、退款成功与退款失败。
2. 预约页需展示预约须知：5 分钟支付时限、2 小时取消分界、退款到账时效、未到店不自动退款。
3. 通知失败不影响业务主流程，只记录日志。

## 14. 竞态与并发
1. 取消与核销并发时，以状态条件更新决定唯一结果，仅一方成功。
2. 状态为 3 时核销一律拦截，提示存在待处理取消申请。
3. 重复核销、重复完成必须幂等拦截，不重复计收入。
4. ❌ 禁止出现既退款又核销、或同一预约两条核销记录。

## 15. 状态同步补偿
1. 详情页提供“同步订单状态”能力，后端主动查询渠道真实交易状态，补偿回调丢失。
2. 查询结果与本地不一致时，按支付流水与状态机规则修正，且必须幂等。
3. 补偿不得越权修改已取消、已核销订单。

## 16. Go 代码规范
1. GoFrame 分层：controller / service / repo；状态用常量，禁止硬编码数字。
2. 建单走事务，事务提交后才操作 Redis。
3. 业务校验统一收敛到 Skill 层，前端隐藏按钮只是辅助，后端必须二次校验。
4. SQL 参数绑定，禁止拼接。
5. 日志覆盖：建单、占名额、超时释放、支付回调、幂等拦截、取消申请、退款。

## 17. C 端文案
- 预约成功：预约成功，名额保留 5 分钟，请尽快完成支付
- 名额已满：该时段名额已抢光，请选择其他时段
- 宠物重复：该宠物已预约本时段，请勿重复预约
- 时段已开始：该时段已开始，无法预约
- 超时关闭：预约超时未支付，订单已自动取消，名额已释放
- 支付处理中：支付请求处理中，请勿重复点击
- 支付成功：支付成功，预约已确认，请按时到店
- 取消需审核：已提交取消申请，等待客服审核，审核期间门店无法核销
- 重复提交：取消申请审核中，请勿重复提交
- 退款失败：退款失败，请联系客服跟进，预约状态不受影响
- 未到店：门店已标记本次未到店，本次预约不自动退款

## 19. 红线禁止清单
❌ 先扣名额后建单，或支付成功才扣名额
❌ 状态跳级流转，待审核直接核销
❌ 状态 3 释放名额
❌ 退款失败后恢复预约或重占名额
❌ C 端开放任何 B 端能力
❌ 绕过 `pet_id + slot_id` 唯一约束
❌ 时段已开始仍接受预约
❌ 定时任务处理非状态 1 订单
❌ 取消与核销并发两方都成功
❌ 同一待支付订单并发生成多笔支付单
❌ 同一交易号重复通知当成重复扣款退款
❌ 两条不同交易号通知都确认预约
❌ 重复支付退款复用取消成功状态或释放名额
❌ 用前端时间判定取消阈值
❌ 允许同一预约重复提交取消申请
❌ 支持部分退款或擅自修改退款金额
❌ 回调丢失后人工改状态而不走渠道查询
